## Problem Statement

The open-source, local-first ATS Agent must turn a candidate's master CV and supplied job list into truthful, per-role proposals. It should also use the existing AI Job Search workspace to discover additional public jobs, capture each role description through the existing public Scrapling path, identify the role's real requirements, and improve evidence-backed wording and keyword coverage. An end-to-end run exposed four immediate failures: third-party job links were labelled as official sources; generic and duplicate requirements diluted the useful evidence-gap list; the review page buried the few actionable changes among disabled cards; and an empty capture stopped without a structured recovery path. These failures can mislead a candidate without changing their CV.

## Demand Evidence

The intended user asked to use the tool end to end with their CV, inspect the drawbacks, plan upgrades, and implement them. The product must earn trust in a high-consequence job-search workflow: it helps candidates present truthful evidence to an employer, but it must not fabricate qualifications, guarantee screening outcomes, or apply automatically.

## Status Quo

AI Job Search already owns portal discovery, including an enabled low-volume LinkedIn public-job skill; it stores a read-only discovery export in `job_scraper/seen_jobs.json`. `ats-agent research-jobs` currently captures a supplied list's role text, maps requirements to CV evidence, and creates reviewable proposal artifacts. The user can approve selected proposal changes and apply them only through the digest-bound approval flow. In the tested run, eight role proposals were digest-valid and the source CV hash remained unchanged; one role was blocked by an insufficient capture.

## Intended End-to-End Flow

```
master CV + candidate evidence ──> evidence ledger ───────┐
provided job list ────────────────────────────────────────┤
AI Job Search discovery export (including existing LinkedIn skill) ─> read-only import
                                                          │
all discovered roles ─> public Scrapling capture ─> sourced requirements
                                                          │
evidence-bound mapping ─> draft proposal + gaps + review ─> explicit approval ─> new tailored copy + validation
```

AI Job Search remains the discovery owner; `ats-agent` does not write its tracker or submit applications. Discovery results are retained without score, location, language, or prestige filtering. A role has one lifecycle status (`imported`, `expired`, `blocked_import`, `blocked_capture`, or `proposal_draft`) plus zero-or-more warnings (such as eligibility), so warnings never replace workflow state. No role is silently discarded. Batches remain bounded for predictable local runtime: the first 20 legacy-import roles are captured by default, every later row stays visibly imported, and repeatable stable `--job-id` selections permit an explicit later or larger batch.

## Target User & Narrowest Wedge

The initial user is an evidence-conscious student or early-career applicant with a master CV containing their full, truthful history. The narrowest wedge is a reviewable, per-role CV proposal that clearly distinguishes source provenance, candidate-supported changes, unsupported gaps, and capture recovery—before any document is produced. "ATS readiness" means a transparent coverage check against the captured role text, not a prediction or guarantee that any employer's system will pass the CV.

## Constraints

- Keep `ats-agent` as the canonical engine and retain the existing `PROPOSE -> EXPLICIT APPROVAL -> APPLY -> VALIDATE` boundary.
- Treat job pages and extracted text as untrusted role evidence, never as candidate evidence.
- Preserve the source CV and its formatting unless a verified, explicitly approved proposal is applied to a new output file.
- Do not add claims, metrics, skills, qualifications, work authorization, or keywords without candidate evidence; an unsupported keyword is a development gap, not tailoring material.
- Reuse the existing AI Job Search discovery workspace and its installed LinkedIn skill; do not add another LinkedIn scraper or bypass portal controls.
- Retain every discovered/provided role with a visible status; do not impose fit, location, language, salary, or prestige filters in the ATS Agent pipeline.
- Do not add a crawler, database, web service, ATS-bypass claim, or automatic job application feature.
- Reuse the existing CLI, proposal schema, requirement mapper, review renderer, and tests wherever possible.

## Premises

- Correct provenance is more valuable than a superficially complete job record: `official_job_page` must mean a verified employer-owned URL.
- A candidate needs a concise decision surface first; the full audit matrix belongs behind that decision, not ahead of it.
- Repeated or generic requirements create noise, so canonicalization and qualification-aware ranking improve the review without changing underlying evidence.
- Capture failure is normal on public job sites; an explicit, provenance-labelled fallback is safer than silently treating an aggregator as official.
- The best safe screening outcome is clearer, truthful relevance: structured coverage, supported wording, and honest gaps—not a claimed or engineered pass rate.

## Approaches Considered

### Documentation-only trust patch

Add warnings to the current output without changing classification, mapping, or recovery. Rejected because a warning cannot prevent misleading source labels or make the decision surface usable.

### New role-dossier subsystem

Create a separate per-role data model, persistence layer, and rich web UI. Rejected as unnecessary architecture: the existing proposal and review artifacts already provide the required integration points.

### Repair the core flow

Correct source classification at capture time, canonicalize and classify requirements before ranking, render a compact decision summary above the existing matrix, and emit a structured recovery request when capture is insufficient. Selected because it fixes the observed root causes in the single existing pipeline.

## Recommended Approach

Implement four small, compatible changes in the shared pipeline:

1. Classify provenance from the captured URL and explicitly label third-party/aggregator sources; only verified employer domains may be `official_job_page`.
2. Extend the existing job-list parser to read AI Job Search's `seen_jobs.json` read-only export alongside current JSON and Markdown lists. Map its title/company/url/status/portal fields without mutating the discovery workspace or filtering rows.
3. Canonicalize duplicate and generic requirements, separate eligibility/qualification requirements from skills, and rank gaps so the user sees specific, decision-relevant work first.
4. Add an actionable proposal summary to `review.html`: selectable changes first, count and reason for unavailable changes, then collapsible detail for the audit matrix and gaps.
5. Produce a machine-readable recovery request for insufficient captures, preserving the original URL and listing acceptable user-supplied or verified alternate inputs without converting them to official evidence.

The existing approval digest remains the sole authority for application; these features cannot auto-select, approve, apply, or submit anything.

## Compatibility Contracts

- Each captured source records `url`, `captured_at`, `method`, `sha256`, `extraction_status`, and `source_type`. Permitted values are `official_job_page`, `third_party_job_page`, `official_company_context`, and `aggregator_fallback`. `aggregator_fallback` is a source type used only for a user-supplied fallback. `official_job_page` requires an explicit `official_job_host` plus a public `official_host_verification_url` in the local job record; the captured job URL must match that host and the verification URL host. Host comparison is normalized exact hostname equality (case-folded, trailing-dot removed, IDNA-normalized; ports excluded; no suffix or subdomain matching). The job-list author makes this auditable local assertion after checking the employer; the tool does not authenticate domain ownership. Both input fields and their capture hashes remain in the manifest for audit. A non-matching or absent signal is `third_party_job_page`; the classifier never infers official status.
- Existing proposal JSON remains compatible. The capture recovery request is a new `capture-recovery.json` sidecar in the blocked role directory, containing `status`, `original_url`, `reason`, and an `accepted_inputs` list. It is not a proposal and cannot be approved or applied.
- The AI Job Search import accepts the legacy top-level `seen` object and, if present, only a declared supported `schema_version`. Every source row gets a stable discovery identity from `portal + original seen key`; its ATS Agent job ID is a deterministic hash of that identity. A duplicate identity or generated-ID collision is retained as a `blocked_import` row with its source reference, never merged or overwritten. A public `url` maps to the current job-list shape, `title` becomes `role`, `portal` is preserved as discovery provenance, and the original discovery status is retained as metadata. Missing/invalid `seen`, unsupported versions, malformed rows, or unsafe URLs are reported in the import manifest without writing to `seen_jobs.json` or the application tracker.
- Requirement deduplication uses the existing normalized-term vocabulary: collapse same canonical term and category, retain the strongest importance, and preserve source spans. Generic terms (`master`, `remote`, `work authorization`, and `professional experience`) remain eligibility/qualification records rather than screening-keyword gaps. Gap ranking is mandatory first, then specific multiword/technical terms, then ID for deterministic ties.
- The review page uses native `<details>`/`<summary>` for the full matrix and gap detail. Its initial section contains supported proposal changes and a count/reason for unavailable changes; selecting a checkbox only prepares the existing schema-v2 digest-bound approval manifest. `ats-agent apply` remains its sole consumer and revalidates the proposal path, digest, supported selections, and document constraints before writing any output.

## Candidate Gap Confirmation

- Every unsupported, role-relevant requirement can surface a concise question: whether the candidate genuinely has the experience and can substantiate it. The question names the captured requirement and never presupposes a positive answer.
- A "yes" is followed by concrete candidate-provided detail: what they did, the setting/timeframe, their contribution, and any supportable result or artifact. A bare affirmation never becomes CV text.
- A sufficient answer requires a confirmed activity plus its setting or timeframe; result/artifact is optional when unavailable. It is stored as a hashed, candidate-provided supplemental-evidence artifact in the evidence ledger and its ID/hash is included in every resulting draft change and the proposal digest. It may support a new **draft** change only; it does not modify the master CV, approve a change, or apply a document.
- Correction or withdrawal of supplemental evidence creates a fresh proposal and digest, so any prior approval manifest fails digest validation rather than applying stale content.
- A "no", refusal, contradiction, or insufficient detail leaves the item as an unsupported gap and offers a development/research recommendation. The user can correct or withdraw supplemental evidence before proposal approval.

## Open Questions

- Employer-domain verification uses an explicit local record plus a captured public verification URL; complex corporate-domain registries, redirects, and subsidiary inference are out of scope until real examples show that need.
- The recovery input may be structured in artifacts now, while interactive CLI collection can remain a documented manual step until users demonstrate repeated friction.
- Discovery search configuration remains in AI Job Search. The existing LinkedIn portal skill is used only under its public, low-volume, personal-use constraints; adding a separate LinkedIn scraper is not justified.

## Success Criteria

- A LinkedIn or other third-party source is never emitted as `official_job_page`; an employer-owned source remains correctly classified.
- A real or fixture AI Job Search `seen_jobs.json` imports every valid source row without changing the discovery file or application tracker; LinkedIn discovery URLs remain third-party provenance unless separately verified.
- Duplicate and generic requirements do not crowd out specific gaps in the rendered review decision summary.
- A reviewer can identify every selectable proposal change and why other changes are unavailable without scanning the full matrix.
- An insufficient capture produces a structured, provenance-labelled recovery artifact with the original source URL.
- A supported candidate response produces only a draft, clearly candidate-provided proposal change; a bare "yes" and a declined response cannot alter a CV proposal.
- Correcting or withdrawing candidate supplemental evidence invalidates the previous digest-bound approval path and requires a fresh draft.
- Focused fixtures cover employer-host match vs LinkedIn URL, absent and mismatched verification-host signals, an `aggregator_fallback`, a no-filter AI Job Search import with duplicates and schema drift, separate lifecycle/warning rendering, duplicate/generic ranking, a summary with one supported and one unavailable change, an insufficient capture recovery artifact, and candidate gap responses for sufficient, bare-yes, declined, contradictory, corrected, and withdrawn evidence.
- Regression tests cover each behavior; full project linting, typing, unit, benchmark, adapter, build, and browser checks pass.
- The tested source CV hash remains unchanged, and no tailored CV is created without explicit selection and approval.

## Distribution Plan

Ship through the existing Python package/`ats-agent` CLI and existing Codex and Claude Code adapters. The adapter instructions route discovery to the existing AI Job Search skill first, then pass its read-only export or a supplied list to `ats-agent`. Existing GitHub Actions validate the package, adapters, and multi-platform tests; release remains governed by the current repository process.

## Dependencies

The repair relies on existing AI Job Search portal discovery, job-research, requirement-mapping, proposal-rendering, and document-validation code. It needs no new dependency, crawler, hosted service, or LinkedIn module.

## The Assignment

After the repair passes verification, run one fresh, evidence-bound role proposal and judge the decision summary: approve only changes directly supported by the source CV, and record any provenance or gap classification that still reads ambiguously.
